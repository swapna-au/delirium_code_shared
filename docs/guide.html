Delirium Risk Prediction

Project guide — how everything fits together, and how to run it.

Eastern Health / Monash University  •  data engineering by Carlton St

Start here

One environment, one command. From the repository folder:

conda env create -f environment.yml
conda activate delirium
python run_all.py

Every figure, table, model, and report regenerates into outputs/ and reports/. A full run takes about 40 minutes (the bootstrap is the slow part).

1. What this project does

It predicts, at the point of hospital admission, which patients are likely to develop delirium — using data already collected in the Eastern Health EMR (demographics, observations, pathology, medications, nursing risk screens, and prior diagnoses).

28,565admission episodes
8.0%developed delirium
6–7predictors in the final model
Random Forestprimary model (+ logistic regression)

2. How to run it

You need Anaconda / Miniconda (recommended) or Python 3.10–3.13.

Option A — conda (recommended)

conda env create -f environment.yml
conda activate delirium
python run_all.py

Option B — pip

# Windows
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python run_all.py

# macOS / Linux
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python run_all.py
SHAP note (pip only): the SHAP importance stage needs the shap package, which is awkward to install with pip. The conda environment includes it. With pip, either run pip install shap or just skip that stage — run_all.py continues past it and produces everything else.

4. How the delirium outcome is defined

This is important for the paper, and it was previously unclear, so here it is precisely.

The outcome comes from the recorded diagnosis codes, not from a manual label. The flow is:

  • diagnosis_final_extract.xlsx — a raw query export of the EMR diagnosis table (one row per diagnosis, ~480,000 rows).
  • ingest-diagnosis.py matches each free-text Diagnosis Description against a curated list of delirium descriptions (unspecified delirium, delirium superimposed on dementia, postoperative delirium, delirium tremens, and so on).
  • The flag is aggregated per admission encounter (a logical OR, since a patient may have multiple qualifying diagnosis rows).

So the model target is: “was any delirium diagnosis coded during the encounter?” An admission-timing split (incident vs. prevalent/present-on-admission, using Diagnosis Dt Tm vs. Admission Datetime) was investigated and reverted: for the diagnosis types that carry most delirium codes (Principal Dx / Additional Dx), Diagnosis Dt Tm could not be reliably distinguished from discharge-coding lag (58.7% of these fall within 24h of the discharge date, median 9.7h before discharge), and restricting to diagnosis types with more reliable real-time timestamps (Clinical Dx / Complication) left too few cases (68 rows) to be usable. Given this, the timing split is not reliably identifiable from this data, so all delirium diagnoses (any timing) are retained as outcome-positive — see the manuscript Limitations section for the full analysis. The same script derives comorbidity flags (dementia, COPD, atrial fibrillation, psychiatric disorders, hip fracture) the same way, since those also represent diagnoses coded at any point during the encounter.

diagnosis_final_extract.xlsxraw diagnosis rows
↓
ingest-diagnosis.pymatch delirium descriptions, OR per encounter
↓
delirium flag1 per encounter
Provenance correction: diagnosis_final_extract.xlsx is a direct database query export — it was not derived from the large DAIS1075588.xlsx file. DAIS is a separate data-access extract (ED presentations, inpatient episodes, demographics) that only holds a concatenated diagnosis list per episode, so it could not have produced the granular diagnosis rows. The file diagnosis_filtered.xlsx is a one-off manual Excel check of the delirium codes and is not part of the pipeline.

5. The pipeline stages

StageWhat it does
00_prepare_dataBuilds data/cleaned.csv from the raw bronze join (de-identify + clean). Runs only if the bronze file is present.
01_cross_validation10-fold nested cross-validation with hyperparameter tuning and Platt calibration.
01b_selected_featuresWhich features are selected in each fold (the stable core).
02_bootstrap_validation500-iteration bootstrap with optimism correction (internal validity).
03–05Publication figures: ROC, calibration, decision-curve analysis (+ tables).
05b_threshold_performanceSensitivity / specificity / PPV / NPV across risk thresholds.
06 / 06bSensitivity analyses; subgroup / fairness analysis by sex.
07_figure1(Optional) the manuscript pipeline diagram.
09_model_specificationFull model spec (coefficients, importances, calibration) + saved models.
10_shap_importanceSHAP feature-importance figures.
08_results_reportAssembles the journal-ready Results section (runs last).
eda.pyExploratory descriptive charts (run separately: python eda.py).

6. Where the data lives, and what is safe to share

  • safe data/cleaned.csv is de-identified (all encounter/URN ids, dates, and ward names are removed) and is the only dataset committed to the repository.
  • private the raw extracts and source_file_bronze.csv contain identifiers and live in OneDrive — never in git.
  • The .gitignore blocks everything under data/ except cleaned.csv, so raw patient data cannot be committed by accident.

9. Working with git (the basics)

  • Get the latest code: git pull
  • See what changed: git status
  • Running the pipeline changes files in outputs/ — that is expected, and git ignores them. You never need to commit anything under outputs/.
  • If git status shows changes to reports/*.md after a run, that is the regenerated report; commit it only if you mean to update the versioned results.
  • When in doubt, do not force anything — ask.
